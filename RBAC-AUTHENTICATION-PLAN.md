## Executive Summary

This document outlines the complete implementation plan for introducing a role-based access control (RBAC) system with JWT authentication to ScholarDock. The system will support:

- **Two role categories**: Admin (Super Admin, General Admin) and User (General User, Pro User, Max User)
- **Email/password authentication** with invite-code-based registration
- **JWT tokens** with 30-day validity and revocation capability
- **Plan-based rate limiting** for AI features, storage, and workspace actions
- **Admin panel** for user management, role assignment, and system configuration
- **Plan information page** showing feature limits for each user tier

**Key Constraint**: The system must remain local-first and privacy-first. User application data stays local; authentication is for access control and feature gating only.

## Requirements Overview

### Functional Requirements

**FR-AUTH-1: User Registration**
- Users must provide email and password
- Registration requires a valid invite code
- Invite codes can only be generated by Super Admin
- New users default to "General User" role
- Email must be unique across all users

**FR-AUTH-2: User Login**
- Users authenticate with email and password
- Successful login returns a JWT token valid for 30 days
- Token must be included in all subsequent API requests
- Failed login attempts should be rate-limited

**FR-AUTH-3: JWT Token Management**
- JWT tokens contain: user_id, email, roles[], token_version, issued_at, expires_at
- Tokens are validated on every protected endpoint
- Tokens can be revoked by Super Admin or General Admin
- Revocation can target specific users or all users (global revoke)
- Revoked users cannot login with their password until admin generates new password

**FR-AUTH-4: Role System**
- **Admin Roles**: Super Admin, General Admin
- **User Roles**: General User, Pro User, Max User
- A user can have both Admin role(s) and User role(s) simultaneously
- Only Super Admin can update roles
- Role changes take effect on next token refresh

**FR-AUTH-5: Invite Code System**
- Super Admin can generate invite codes
- Each invite code has: code (unique), max_uses, used_count, expires_at, created_by
- Invite codes can be single-use or multi-use
- Expired or fully-used codes cannot be used for registration

**FR-AUTH-6: Plan-Based Limits**
Each user plan has specific limits (see detailed table below):
- AI chat messages per session
- Web search availability
- Available AI models
- Agentic action capability
- Total project creation limit
- Total sheet creation limit
- Sheets per project limit
- Records per sheet limit
- Document upload limit (total size or count)
- Sticky notes creation limit
- Whiteboard access
- Chat summarization feature

**FR-AUTH-7: Admin Panel**
- Accessible only to users with Admin role (Super or General)
- New "Admin" tab appears in navigation (above Profile)
- Features:
  - User management (list, search, view details)
  - Role assignment (Super Admin only)
  - Invite code generation (Super Admin only)
  - Token revocation (specific user or global)
  - Password reset (generate random password)
  - View user activity and usage statistics
  - System configuration

**FR-AUTH-8: Plan Information Page**
- Accessible from About section
- Shows comparison table of all User plans (not Admin)
- Displays current user's plan and limits
- Shows usage statistics vs. limits
- Non-authenticated users see generic plan comparison

**FR-AUTH-9: Migration**
- Existing single user (id=1) must be upgraded to Super Admin
- This is a one-time manual migration
- All existing data remains intact

## Role Hierarchy & Permissions

### Role Definitions

#### Admin Roles

**Super Admin**
- **Purpose**: System owner with full control
- **Permissions**:
  - All General Admin permissions
  - Create/update/delete user roles
  - Generate invite codes
  - View all system logs and analytics
  - Configure system-wide settings
  - Cannot be revoked by other admins
- **Limits**: No feature limits (unlimited access)
- **Count**: Should be limited (1-3 per system recommended)

**General Admin**
- **Purpose**: Delegated administrator for user management
- **Permissions**:
  - View all users
  - Revoke user tokens (specific or global)
  - Reset user passwords
  - View user activity logs
  - Cannot modify roles
  - Cannot generate invite codes
- **Limits**: No feature limits (unlimited access)

#### User Roles

**General User** (Free Tier)
- **Purpose**: Basic access for evaluation and light usage
- **Target Audience**: New users, casual applicants

**Pro User** (Mid Tier)
- **Purpose**: Enhanced features for active applicants
- **Target Audience**: Users managing multiple applications

**Max User** (Premium Tier)
- **Purpose**: Full feature access for power users
- **Target Audience**: Users managing complex application portfolios

### Role Assignment Rules

1. **Default Role**: New registrations default to "General User"
2. **Multiple Roles**: A user can have both Admin and User roles
   - Example: `roles: ["super_admin", "max_user"]`
   - Admin permissions apply for admin actions
   - User plan limits apply for workspace features
3. **Role Updates**: Only Super Admin can modify roles
4. **Role Validation**: Backend validates role on every request
5. **Admin Bypass**: Users with any Admin role bypass User plan limits

### Feature Descriptions

**AI Chat Messages/Session**
- Counts messages sent by user in a single conversation session
- Resets when user starts a new conversation
- Enforced per conversation thread
- Does not count AI responses, only user messages

**AI Chat Messages/Day**
- Counts total AI messages sent by user across all conversations in a 24-hour period
- Resets at midnight UTC
- Provides a daily usage cap to prevent excessive API costs
- Tracked independently from per-session limits

**AI Chat Messages/Month**
- Counts total AI messages sent by user across all conversations in a calendar month
- Resets on the 1st of each month at midnight UTC
- Provides a monthly usage cap for long-term cost control
- Tracked independently from per-session and daily limits

**Web Search/Day**
- Daily limit for web search requests
- Resets at midnight UTC
- Counts each web search request (not individual results)
- Failed searches don't count toward limit

**Web Search/Month**
- Monthly limit for web search requests
- Resets on the 1st of each month at midnight UTC
- Provides long-term usage control for web search API costs
- Tracked independently from daily limits

**Total Records (All Sheets)**
- Cumulative limit for total number of records across all sheets
- Prevents database bloat and ensures performance
- Deleting records frees up quota
- Tracked across all projects and sheets
- Daily limit resets at midnight UTC
- Counts each web search request (not individual results)
- Failed searches don't count toward limit

**Available AI Providers & Models**
- **Provider Access**: General users get 1 provider, Pro users get 2 providers, Max users and Admins get all 4 providers
- **Model Tiers**:
  - **Fast models** (General User): GLM-4.7, gemini-2.5-flash-lite, groq/openai/gpt-oss-20b, devstral-2512
  - **Standard models** (Pro User): + GLM-5-Turbo, gemini-2.5-flash, llama-3.3-70b-versatile, mistral-medium-3-5
  - **Premium models** (Max User): + GLM-5.1, GLM-5, gemini-2.5-pro, groq/compound, mistral-large-latest
- **Provider Selection**: Backend automatically selects first available configured provider if user doesn't specify
- **Model Format**: Users specify models as `provider:model` (e.g., `gemini:gemini-2.5-flash`, `groq:llama-3.3-70b-versatile`)

**Agentic Actions**
- Read-only: Can query data, analyze, fetch summaries (no mutations)
- Full access: Can create, update, delete workspace items

**Document Uploads**
- Tracks cumulative size of all uploaded files
- Deleting files frees up quota

**Whiteboard Access**
- General and Pro users cannot access whiteboard feature at all
- Max users can create up to 10 whiteboards

### Limit Enforcement Strategy

**Backend Enforcement:**
1. **Pre-request validation**: Check limits before processing action
   ```python
   # Pseudo-code
   user_role = get_primary_user_role(user)  # e.g., 'pro_user'
   role_limit = get_role_limit(user_role, 'ai_messages')  # {count: 30, reset_period: 'daily'}
   user_usage = get_user_usage(user.id, 'ai_messages')  # {current_count: 28, last_reset_at: '2026-05-30 00:00:00'}
   
   # Check if reset needed
   if should_reset(user_usage.last_reset_at, role_limit.reset_period):
       reset_user_usage(user.id, 'ai_messages')
       user_usage.current_count = 0
   
   # Check limit (immediate effect of admin changes)
   if role_limit.limit_count != -1 and user_usage.current_count >= role_limit.limit_count:
       raise LimitExceededError(f"AI message limit reached ({user_usage.current_count}/{role_limit.limit_count})")
   ```

2. **Atomic counters**: Use database transactions for accurate counting
3. **Automatic reset**: Check reset period on every request, reset if needed
4. **Dynamic limit updates**: Always fetch latest role_limit from DB (no caching of limits)
5. **Clear error messages**: Return specific limit exceeded errors with current usage and limit
6. **Admin bypass**: Skip limit checks for Admin roles (super_admin, general_admin)

**Frontend Enforcement:**
1. **Proactive UI disabling**: Disable buttons when limit reached
2. **Usage indicators**: Show current usage vs. limit (e.g., "8/10 messages today")
3. **Reset timer**: Show when quota resets (e.g., "Resets in 6 hours")
4. **Upgrade prompts**: Suggest plan upgrade when limit approached
5. **Real-time updates**: Refresh usage after each action
6. **Immediate reflection**: Poll or websocket to reflect admin limit changes immediately

## Database Schema Changes

### New Tables

#### 1. `users` (replaces/extends `local_profiles`)

```sql
CREATE TABLE IF NOT EXISTS users (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  email TEXT NOT NULL UNIQUE,
  password_hash TEXT NOT NULL,
  display_name TEXT NOT NULL DEFAULT 'User',
  avatar TEXT,
  roles TEXT NOT NULL DEFAULT '["general_user"]', -- JSON array
  token_version INTEGER NOT NULL DEFAULT 1,
  is_active INTEGER NOT NULL DEFAULT 1,
  last_login_at TEXT,
  created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE INDEX idx_users_email ON users(email);
CREATE INDEX idx_users_token_version ON users(token_version);
```

**Fields:**
- `email`: Unique identifier for login
- `password_hash`: bcrypt hash of password
- `roles`: JSON array of role strings (e.g., `["super_admin", "max_user"]`)
- `token_version`: Incremented on revocation to invalidate all tokens
- `is_active`: Soft delete flag (0 = deactivated, cannot login)
- `last_login_at`: Timestamp of last successful login

#### 2. `invite_codes`

```sql
CREATE TABLE IF NOT EXISTS invite_codes (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  code TEXT NOT NULL UNIQUE,
  max_uses INTEGER NOT NULL DEFAULT 1,
  used_count INTEGER NOT NULL DEFAULT 0,
  expires_at TEXT,
  created_by INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE INDEX idx_invite_codes_code ON invite_codes(code);
CREATE INDEX idx_invite_codes_expires_at ON invite_codes(expires_at);
```

**Fields:**
- `code`: Unique invite code string (e.g., "SCHOLAR-2026-ABC123")
- `max_uses`: Maximum number of registrations allowed (-1 = unlimited)
- `used_count`: Current number of times used
- `expires_at`: Optional expiration timestamp (NULL = never expires)
- `created_by`: User ID of Super Admin who created the code

CREATE TABLE IF NOT EXISTS user_sessions (

## Authentication Flow

### Registration Flow

```
User → Frontend Registration Form
  ↓
  [email, password, invite_code]
  ↓
Backend: POST /auth/register
  ↓
  1. Validate invite code (exists, not expired, not fully used)
  2. Validate email (unique, valid format)
  3. Validate password (min 8 chars, complexity rules)
  4. Hash password with bcrypt
  5. Create user record with default role ["general_user"]
  6. Increment invite_code.used_count
  7. Create user_usage_stats record
  8. Return success (no auto-login, redirect to login)
  ↓
Frontend: Redirect to login page
```

**Validation Rules:**
- Email: Valid format, unique, max 255 chars
- Password: Min 8 chars, at least 1 uppercase, 1 lowercase, 1 number, 1 special char
- Invite code: Must exist, not expired, used_count < max_uses (or max_uses = -1)

### Login Flow

```
User → Frontend Login Form
  ↓
  [email, password]
  ↓
Backend: POST /auth/login
  ↓
  1. Find user by email
  2. Verify password with bcrypt
  3. Check is_active = 1
  4. Generate JWT token:
     - user_id
     - email
     - roles (array)
     - token_version
     - jti (unique token ID)
     - iat (issued at)
     - exp (expires at: now + 30 days)
  5. (Optional) Create user_sessions record
  6. Update users.last_login_at
  7. Return JWT token + user info
  ↓
Frontend: Store token in localStorage/sessionStorage
Frontend: Redirect to dashboard
```

**Rate Limiting:**
- Max 5 failed login attempts per email per 15 minutes
- Implement exponential backoff after 3 failures
- Log suspicious activity (many failed attempts)

### Token Validation Flow (Every Protected Request)

```
Frontend → Backend: API Request with Authorization header
  ↓
  Authorization: Bearer <jwt_token>
  ↓
Backend Middleware: validate_token()
  ↓
  1. Extract token from header
  2. Verify JWT signature
  3. Check expiration (exp)
  4. Decode payload
  5. Fetch user from database by user_id
  6. Verify user.is_active = 1
  7. Verify token_version matches user.token_version
  8. (Optional) Check user_sessions.revoked_at is NULL
  9. Attach user object to request context
  ↓
Backend: Process request with authenticated user
```

**Token Validation Errors:**
- 401 Unauthorized: Invalid/expired/revoked token
- 403 Forbidden: Valid token but insufficient permissions

### Logout Flow

```
User → Frontend: Click logout
  ↓
Frontend: POST /auth/logout (optional)
  ↓
Backend: (Optional) Mark user_sessions.revoked_at
  ↓
Frontend: Clear token from storage
Frontend: Redirect to login page
```

**Note**: Since JWT is stateless, logout is primarily client-side. Server-side session revocation is optional but recommended for security.

## JWT Token Management

### Token Structure

```json
{
  "user_id": 123,
  "email": "user@example.com",
  "roles": ["general_user"],
  "token_version": 1,
  "jti": "unique-token-id-uuid",
  "iat": 1717027200,
  "exp": 1719619200
}
```

**Fields:**
- `user_id`: Primary key from users table
- `email`: User's email (for display, not auth)
- `roles`: Array of role strings for permission checks
- `token_version`: Current version from users.token_version
- `jti`: JWT ID for individual token revocation
- `iat`: Issued at timestamp (Unix epoch)
- `exp`: Expiration timestamp (Unix epoch, 30 days from iat)

### Token Revocation Strategies

#### Strategy 1: Token Version (Global Revoke)

**How it works:**
1. Each user has a `token_version` field (starts at 1)
2. JWT includes current `token_version` in payload
3. On validation, compare JWT's `token_version` with DB's `token_version`
4. If mismatch, token is invalid

**Revoke all tokens for a user:**
```sql
UPDATE users SET token_version = token_version + 1 WHERE id = ?;
```

**Pros:**
- Simple implementation
- No additional tables needed
- Fast validation (single DB lookup)

**Cons:**
- Revokes ALL tokens for a user (no granular control)
- User must re-login after revocation

#### Strategy 2: Session Tracking (Granular Revoke)

**How it works:**
1. Store each token in `user_sessions` table with `jti`
2. On validation, check if `user_sessions.revoked_at` is NULL
3. Can revoke individual sessions by setting `revoked_at`

**Revoke specific token:**
```sql
UPDATE user_sessions SET revoked_at = CURRENT_TIMESTAMP WHERE token_jti = ?;
```

**Pros:**
- Granular control (revoke specific sessions)
- Can show "active sessions" to users
- Better audit trail

**Cons:**
- Additional DB query on every request
- Table grows over time (needs cleanup)
- More complex implementation

#### Strategy 3: Hybrid (Recommended)

**Combine both strategies:**
- Use `token_version` for global revoke (all user's tokens)
- Use `user_sessions` for granular revoke (specific tokens)
- Validation checks both:
  1. JWT `token_version` == DB `token_version`
  2. `user_sessions.revoked_at` IS NULL

**Benefits:**
- Fast global revoke (increment version)
- Optional granular revoke (mark session)
- Flexible for different admin actions

### Token Refresh Strategy

**Option A: No Refresh (30-day expiration)**
- Tokens expire after 30 days
- User must re-login
- Simpler implementation

**Option B: Refresh Token (Recommended for production)**
- Issue short-lived access token (1 hour) + long-lived refresh token (30 days)
- Use refresh token to get new access token
- More secure (shorter exposure window)

**For MVP: Use Option A** (no refresh, 30-day expiration)

## Security Considerations

### Password Security

1. **Hashing**: Use bcrypt with cost factor 12
2. **Complexity Requirements**:
   - Minimum 8 characters
   - At least 1 uppercase letter
   - At least 1 lowercase letter
   - At least 1 number
   - At least 1 special character
3. **Storage**: Never store plaintext passwords
4. **Transmission**: Always use HTTPS in production

### JWT Security

1. **Secret Key**: Use strong random secret (256-bit minimum)
2. **Algorithm**: Use HS256 or RS256
3. **Expiration**: 30 days (configurable)
4. **Storage**: Store in httpOnly cookie (preferred) or localStorage (acceptable for local app)
5. **Validation**: Verify signature, expiration, and token_version on every request

### Token Revocation

1. **Version-based**: Increment token_version to invalidate all user tokens
2. **Session-based**: Mark specific sessions as revoked
3. **Cleanup**: Periodically delete expired sessions from database

### Rate Limiting

1. **Login Attempts**: Max 5 per email per 15 minutes
2. **Registration**: Max 3 per IP per hour
3. **API Requests**: Max 100 per user per minute (configurable by plan)

### Invite Code Security

1. **Uniqueness**: Generate cryptographically random codes
2. **Format**: `SCHOLAR-YYYY-XXXXXX` (e.g., `SCHOLAR-2026-A3F9K2`)
3. **Expiration**: Optional expiration date
4. **Usage Tracking**: Prevent reuse beyond max_uses

### Admin Action Auditing

1. **Log All Admin Actions**: Role changes, token revocations, password resets
2. **Include Context**: Admin user, target user, timestamp, IP address
3. **Immutable Logs**: Audit logs should not be editable
4. **Retention**: Keep logs for at least 90 days

### CORS Configuration

Since this is a local-first app:
- Backend: `http://localhost:<backend-port>`
- Frontend: `http://localhost:<frontend-port>`
- Allow credentials for cookie-based auth
- Restrict origins to localhost in production

### SQL Injection Prevention

1. **Parameterized Queries**: Always use parameter binding
2. **ORM/Query Builder**: Use SQLAlchemy or similar
3. **Input Validation**: Validate all user inputs
4. **Escape Special Characters**: Especially in search queries

### XSS Prevention

1. **Output Encoding**: Escape HTML in user-generated content
2. **Content Security Policy**: Set CSP headers
3. **Sanitize Inputs**: Especially for rich text fields

### 1. Password Reset Flow

**Question**: How should users reset their own passwords?

**Options**:
- A) Admin-only password reset (current plan)
- B) Email-based password reset (requires email service)
- C) Security questions
- D) No self-service reset (contact admin)

**Recommendation**: Start with A (admin-only), add B in future if email service is added

### 2. Multi-Device Sessions

**Question**: Should users be able to see and manage their active sessions?

**Options**:
- A) Yes, show all active sessions with device info
- B) No, only admins can see sessions
- C) Show session count only, no details

**Recommendation**: A (user-facing session management is good UX)

### 3. Plan Upgrade Flow

**Question**: How do users upgrade their plan?

**Options**:
- A) Contact admin (manual upgrade)
- B) Self-service upgrade (future payment integration)
- C) Automatic upgrade based on usage
- D) No upgrades (admin assigns plans)

**Recommendation**: A for MVP (manual), B for future

### 4. Usage Quota Reset

**Question**: When should usage quotas reset?

**Solution**: Admin-configurable quota system with flexible reset periods

**Implementation**:
- Each limit has two components: **count** (numeric limit) and **reset_period** (time-based reset)
- Reset period options: `per_session`, `hourly`, `daily`, `weekly`, `monthly`, `yearly`, `never` (cumulative)
- Admins can configure both count and reset period per role per feature
- Changes take effect immediately - users get more/less quota based on current usage vs new limit

**Examples**:
- AI messages: 100 per day (resets at midnight UTC)
- Web searches: 20 per day (resets at midnight UTC)
- Projects: 50 never (cumulative, must delete to free quota)
- Documents: 5GB never (cumulative, deletion frees quota)

**Dynamic Limit Updates**:
- **Scenario 1**: Limit increased from 100 to 120, user used 100
  - User immediately gets 20 more (120 - 100 = 20 available)
- **Scenario 2**: Limit decreased from 100 to 50, user used 80
  - User cannot use feature until usage drops below 50 (must delete items or wait for reset)
- **Scenario 3**: Limit decreased from 100 to 50, user used 30
  - User can still use 20 more (50 - 30 = 20 available)

**Storage**:
- Limits stored in `role_limits` table (role-specific, centralized)
- User usage tracked in `user_usage_stats` table (per-user counters)
- Validation: `current_usage < role_limit` checked on every action

### 5. Soft Delete vs Hard Delete

**Question**: When a user is deactivated, what happens to their data?

**Options**:
- A) Soft delete (is_active=0, data preserved)
- B) Hard delete (user and all data removed)
- C) Soft delete user, optionally delete data
- D) Archive data, then delete user

**Recommendation**: A (soft delete) - allows reactivation without data loss

### 6. Token Storage

**Question**: Where should JWT tokens be stored in the frontend?

**Options**:
- A) localStorage (simple, persists across tabs)
- B) sessionStorage (more secure, single tab)
- C) httpOnly cookie (most secure, requires backend support)
- D) In-memory only (most secure, no persistence)

**Recommendation**: A for MVP (localStorage), C for production (httpOnly cookie)

### 7. Invite Code Format

**Question**: What format should invite codes use?

**Current Plan**: `SCHOLAR-YYYY-XXXXXX` (e.g., `SCHOLAR-2026-A3F9K2`)

**Alternatives**:

- C) Readable phrase: `purple-elephant-42`

**Recommendation**: Keep current plan (branded, readable, unique)

### 8. Admin Self-Revocation

**Options**:
- A) Per-user (requires authentication)

- C) Both (most secure)

**Recommendation**: C (per-IP for login/register, per-user for authenticated endpoints)

-- Users table (replaces/extends local_profiles)
CREATE TABLE IF NOT EXISTS users (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  email TEXT NOT NULL UNIQUE,
  password_hash TEXT NOT NULL,
  display_name TEXT NOT NULL DEFAULT 'User',
  avatar TEXT,
  roles TEXT NOT NULL DEFAULT '["general_user"]', -- JSON array
  token_version INTEGER NOT NULL DEFAULT 1,
  is_active INTEGER NOT NULL DEFAULT 1,
  last_login_at TEXT,
  created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE INDEX idx_users_email ON users(email);
CREATE INDEX idx_users_token_version ON users(token_version);
CREATE INDEX idx_users_is_active ON users(is_active);

-- Invite codes table
CREATE TABLE IF NOT EXISTS invite_codes (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  code TEXT NOT NULL UNIQUE,
  max_uses INTEGER NOT NULL DEFAULT 1, -- -1 for unlimited
  used_count INTEGER NOT NULL DEFAULT 0,
  expires_at TEXT,
  created_by INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE INDEX idx_invite_codes_code ON invite_codes(code);
CREATE INDEX idx_invite_codes_expires_at ON invite_codes(expires_at);
CREATE INDEX idx_invite_codes_created_by ON invite_codes(created_by);

-- User sessions table (for granular token revocation)
CREATE TABLE IF NOT EXISTS user_sessions (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  user_id INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  token_jti TEXT NOT NULL UNIQUE,
  ip_address TEXT,
  user_agent TEXT,
  expires_at TEXT NOT NULL,
  revoked_at TEXT,
  created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE INDEX idx_user_sessions_user_id ON user_sessions(user_id);
CREATE INDEX idx_user_sessions_token_jti ON user_sessions(token_jti);
CREATE INDEX idx_user_sessions_expires_at ON user_sessions(expires_at);
CREATE INDEX idx_user_sessions_revoked_at ON user_sessions(revoked_at);

-- Role limits table (centralized, admin-configurable)
CREATE TABLE IF NOT EXISTS role_limits (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  role TEXT NOT NULL,
  feature TEXT NOT NULL,
  limit_count INTEGER NOT NULL DEFAULT -1,
  reset_period TEXT NOT NULL DEFAULT 'never',
  created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
  UNIQUE(role, feature)
);

CREATE INDEX idx_role_limits_role ON role_limits(role);
CREATE INDEX idx_role_limits_feature ON role_limits(feature);
CREATE UNIQUE INDEX idx_role_limits_role_feature ON role_limits(role, feature);

-- User usage statistics table (per-user tracking)
CREATE TABLE IF NOT EXISTS user_usage_stats (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  user_id INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  feature TEXT NOT NULL,
  current_count INTEGER NOT NULL DEFAULT 0,
  last_reset_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
  UNIQUE(user_id, feature)
);

CREATE INDEX idx_user_usage_stats_user_id ON user_usage_stats(user_id);

CREATE UNIQUE INDEX idx_user_usage_stats_user_feature ON user_usage_stats(user_id, feature);

## Summary

This comprehensive plan outlines the complete implementation of a role-based access control (RBAC) system with JWT authentication for ScholarDock. The system introduces:

- **5 distinct roles** with granular permissions and limits
- **Invite-code-based registration** controlled by Super Admins
- **JWT authentication** with 30-day validity and revocation capability
- **Plan-based feature limits** enforced across all workspace actions
- **Full-featured admin panel** for user and system management
- **Plan comparison page** for users to understand their limits

The implementation is designed to maintain ScholarDock's core principles:
- **Local-first**: All user data remains on the local machine
- **Privacy-first**: Authentication is for access control only
- **Zero infrastructure cost**: Uses local SQLite and file storage
- **AI-maintainable**: Clear structure and comprehensive documentation

The phased implementation approach allows for incremental development and testing, with a target completion of 6 weeks for a production-ready system.
